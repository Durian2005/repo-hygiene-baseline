# repo-hygiene-baseline

给**已经写了一段时间、还能救**的项目做第一批整理（"织网"）：
引入最小规则集 linter、核查行尾与 `.gitattributes`、给脚本目录做分类索引、把证据/截图归档。

这是一份给 AI 编码助手（WorkBuddy / Claude Code / CodeBuddy 等）加载的 Skill，
核心就 `SKILL.md` 一个文件。当然它也能当整理手册直接读。

## 核心主张：按"谁是别人的安全网"排序，不按"看起来多严重"排序

| 批次 | 内容 | 风险 |
|---|---|---|
| **0 织网** | linter / 行尾与属性 / 脚本目录分类（+ 证据归档） | 低 —— **必须先做** |
| **1 动刀** | 拆分大文件、动结构 | 高 —— 需要回归兜底 |
| **2 扫地** | 文案、目录、副本 | 最低 —— 放最后 |

拆分大文件是唯一的高风险动作，它需要回归兜底；linter 与工具链收口就是那张网。
唯一决定变量是**验收/演示时间**：临近验收时**只做批次 0**，
因为批次 1 要动的往往正是要演示的主线流程。

## 为什么需要它

既有项目整理最容易在几处误判，这份文档记的都是真机实测结论，不只是操作步骤：

- **`w/crlf` 不等于"仓库没统一行尾"**。`core.autocrlf=true` 下"索引 LF / 工作区 CRLF"
  是**零 diff 的正常状态**，但最常见的伪问题形态恰恰就是"一堆 `w/crlf` 文件 + `git status` 干干净净"。
  动手前先 `git ls-files --eol`，判据是 `i/*` 那一段，不是工作区字节。
- **linter 不要上官方全家桶**。8000+ 行的既有前端跑风格规则会一次产出**几百条**告警，
  基线数字没人看，最终一定演变成"加 `--quiet` 或干脆不跑"。
  只开"命中了就是潜在 bug"的规则，实测基线落在**个位数**。
- **脚本目录乱就搬目录是负收益**。脚本之间有相对 import、文档到处引用旧路径，
  搬一次要改一圈；写一份分类索引是零风险的同效做法。
- **禁止"顺手全量 `--fix`"**。交付前跑一次会制造几千行与业务无关的 diff，
  把真正的改动完全埋掉，`git log` 也变得不可读。

## 文档结构

| 章节 | 内容 |
|---|---|
| 一 | 加 linter：最小规则集取舍、存量告警只要求"增量"、lint 上线即抓真缺陷 |
| 二 | 行尾与 `.gitattributes`：`git ls-files --eol` 权威判据、什么时候才真的要改 |
| 三 | 脚本目录：用 README 做分类索引，不搬目录 |
| 四 | 证据/截图归档：先找已 ignore 的目录，同步改脚本默认输出 |
| 五 | 收尾必做：构建 + 关键回归、产物目录核查、"已部署产物落后于源码"必须明说 |

## 安装

Clone 到用户级 skills 目录：

```bash
git clone https://github.com/Durian2005/repo-hygiene-baseline.git \
  ~/.workbuddy/skills/repo-hygiene-baseline
```

其他助手请把目录放到各自的 skills 加载路径下，起作用的只有 `SKILL.md`。

## 适用环境

语言与框架无关，示例以 Vue 3 + Vite + ASP.NET Core 的前后端同仓项目为主。
